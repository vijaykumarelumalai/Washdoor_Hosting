1. MODULE ARCHITECTURE & OVERVIEW
--------------------------------------------------------------------------------
Orders v2 is the modern, reactive order management and point-of-sale intake
engine for Washdoor Laundry. Built with React and Material-UI on Vite, and
backed by Supabase (PostgreSQL), Orders v2 replaces fragmented intake screens
with a unified, high-density operational center.

Key Highlights:
- Two-Step Order Wizard: Fast customer lookup/registration, On-Call schedule
  validation, staff assignment, and product catalog cart builder.
- Real-Time Table Workspace: Multi-criteria filtering, live KPI summary cards,
  canonical status mapping, and dynamic services popover.
- 7-Tab Horizontal Stepper: In-place row expansion providing editing across
  customer, order, garment inspection, processing, billing, messages, and review.
- Double-Entry Auditing: Append-only status transitions, immutable activity
  logs, and financial payment ledgers.
- Optional Walk-In Scheduling: Delivery date/time may be added to Walk-In orders
  with future-only validation; On-Call pickup rules remain unchanged.

4. COMPLETE FUNCTIONAL WORKFLOWS
--------------------------------------------------------------------------------

4.1 Step 1 – Order Basics (OrdersV2CreateOrder.jsx)
1. Customer Selection & Address:
   - Two modes: Existing Customer (default) and New Customer.
   - Existing Customer autocomplete searches name, mobile, address, or customer ID
     with a 300ms debounce. Its first action can create a new customer from the
     typed query and extracts a 10-digit mobile when present.
   - Selecting an existing customer validates its name/mobile, then pre-fills name,
     normalized mobile, tag-stripped address, detected address tag, and default
     discount percentage (clamped 0-100).
   - New Customer mode collects customer name and mobile only; validation requires
     a non-blank name and a 10-digit Indian mobile (/^[6-9]\d{9}$/ after normalization).
   - A shared Home/Office/Other chip row and multiline address field are shown in
     both modes. The label is "Address * required" for On-Call and
     "Address (optional for Walk-In orders)" for Walk-In. On save, any existing
     prefix is stripped and the selected tag is re-applied as
     "Home|Office|Other: <address>". A blank Walk-In address is saved as NULL.
2. Order Type:
   - Walk-In: Direct counter drop-off. No Scheduled Pickup; Delivery Date/Time optional.
   - On-Call: Pickup fields are required; delivery fields are optional but validated
     when supplied.
3. On-Call Schedule Validation (validateOnCallSchedule in onCallScheduling.js):
   - New orders: Pickup Date + Time are mandatory and must be strictly in the future.
   - Delivery is optional. If either delivery field is entered, both are required,
     valid, and the delivery must be strictly after pickup.
   - Existing orders are legacy-tolerant: unchanged historical past pickups remain
     editable, but partial values, changed past pickups, or delivery before/at
     pickup are rejected.
4. Walk-In Delivery Schedule Validation (resolveOptionalDelivery in onCallScheduling.js):
   - Delivery Date and Time are optional. Both empty is valid and stores NULL.
   - If only one field is entered, validation fails with
     "Please enter both delivery date and time.".
   - The combined date/time must be in the future relative to the current local
     clock; past or equal values fail with
     "Delivery date and time must be in the future.".
   - The entered date/time is interpreted in the browser's local timezone, then
     converted to an ISO timestamp in scheduled_delivery_at for Supabase.
   - The same validator is used by Create Order, Edit Order, Inline Edit, and
     Side Edit Drawer so validation and error messages remain consistent.
5. Staff Assignment:
   - Attend Staff Name: Optional dropdown from active washdoor_staff_master records;
     blank falls back to "Counter Staff".
   - Assigned Pickup & Delivery Person: Optional dropdown from active
     washdoor_pickup_delivery_master records.
6. Step 1 Footer Actions:
   - Cancel: closes the wizard.
   - Create Order: direct create path. It validates Step 1 and the schedule but
     does not require cart items; it saves with empty items and no primary service
     through the same persistOrder pipeline, without opening Step 2.
   - Continue to Order: validates all Step 1 fields and advances to Step 2.
   - When errors exist, the wizard shows "Please review the highlighted fields
     before continuing." and marks invalid fields inline.

4.2 Step 2 – Build the Order (OrdersV2CreateOrder.jsx)
1. Header Summary:
   - Displays Order ID, Customer, Order type, and Attend Staff chips.
   - A footer Back button returns to Step 1 without losing cart or form data.
2. Garment Catalog (Left Column):
   - Category pills: All, Men, Women, Kids, Home Linen, Accessories.
   - Search matches garment name, category, or item code.
   - Product cards show an SVG illustration, title, category, and unit price
     (₹XX.00 / piece) or red "Price unavailable"; the Add button is disabled when
     no positive price/base_price exists.
   - Service selection and quantity are configured in the cart, not on the card.
3. Order Cart Ledger (Right Column):
   - Each line shows illustration, name, "service • ₹rate each", delete icon,
     service dropdown, quantity stepper, and line total. The same garment and
     service merge when added again.
   - The service dropdown includes "+ Add New Service Type…" which writes directly
     to washdoor_service_types.
   - Clear opens a confirmation dialog with Keep Items / Clear Cart actions.
4. Additional Accordions:
   - Additional Details: care/service notes, internal comments, discount % (0-100),
     and Tax Exemption toggle.
   - Payment / Billing: shown only when at least one payment method is enabled in
     store settings. Includes Payment Status (Paid in Full / Partially Paid /
     Unpaid / Pay on Delivery) which auto-fills advance, payment method, advance
     collected, reference/transaction ID, UPI Instant Pay "SHOW QR", and
     "Mark as Fully Paid".
   - Review & Actions: six-line checklist: Customer, Order type, Staff,
     Items (piece count), Scheduled pickup ("Not required" for Walk-In), and
     Delivery ("Not scheduled" when empty).
5. Real-Time Sticky Footer Summary:
   - Calculates Total Items (lines), Total Pieces, Subtotal, Discount amount,
     GST / Tax (5% or 0%), and Grand Total.
6. Order Saving (persistOrder):
   - The Save Order action re-validates Step 1 and schedule fields and requires at
     least one cart item.
   - Calls createOrderWithCustomer in customerService.js, registers new customers,
     generates ORD0000X, and writes customer_works, washdoor_orders_master, items,
     garment cards, payment ledger, status history, and audit history.
   - Shows a success toast, emits the created payload to onOrderSuccess, closes the
     dialog, and the parent handler calls onRefreshOrders().

4.4 The 7-Tab Horizontal Stepper Inline Edit Workflow
Clicking the expand arrow on any row opens the 7-tab stepper defined by
HORIZONTAL_TABS in OrdersV2List.jsx:
- Tab 1 (Customer Details): Edit customer name, mobile, address, intake method
  (Walk-In / On-Call Pickup), attend staff, assigned pickup & delivery person, and
  a separate Order Priority select. There is no address-type field in this editor.
  Address is required only for On-Call; delivery date/time are shown for both
  methods (Walk-In optional/future-only; On-Call pickup required with delivery
  validated under existing-order rules). The tab footer validity hint checks
  customer name and mobile.
- Tab 2 (Order Details): Blue-themed workspace to change service category,
  use "+ Add New Service Type" (persisting to DB), add garments, and adjust rates/quantities.
- Tab 3 (Garment Inspection): Inspect garments via GarmentInspectionSection:
  fabric, make, condition, stains, damage location, finish preference, and photo uploads.
- Tab 4 (Laundry Processing): Stage tracking (Sorting, Washing, Drying, Ironing, QC, Ready),
  machine assignment, and rack location.
- Tab 5 (Payments & Billing): Recalculate totals, record advance/balance payments,
  select payment modes, and enter transaction reference.
- Tab 6 (Customer Messages): Preview and send automated WhatsApp & SMS templates.
- Tab 7 (Review & Messages): Heading "Review & Confirm Changes" with full change
  review, audit history, and Confirm Changes / Cancel actions.
Save behavior: handleSaveInlineEdit blocks blank On-Call addresses, validates
On-Call schedules in existing-order mode, validates non-On-Call delivery with
resolveOptionalDelivery, composes status/service/payment activity entries into
activity_history/audit_logs/logs plus status_updated_at/by, and calls
updateOrderInSupabase.

4.5 Edit Drawers & Ancillary Modals
- OrdersV2EditDrawer: 5-tab slide-over editor (1. Details, 2. Items, 3. Payments,
  4. Schedule, 5. Notes). Details edits customer/contact, service category, order
  type, status, and address. Items edits line items and pricing. Payments edits
  totals/payment state. Schedule edits expected delivery, On-Call pickup/delivery,
  delivery date/time for all order types, attend staff, and driver. Notes edits
  comments. Save enforces On-Call address, validates schedules, recalculates
  subtotal/tax/total/balance/payment status, appends activity events, and calls
  updateOrderInSupabase.
- SideEditPanel: 6-tab comprehensive panel (1. Order Details, 2. Logistics &
  Factory, 3. Status Updates, 4. Payments, 5. Customer Messages, 6. Comments &
  Audit). It supports Walk-In, On-Call, Home Delivery, Express, and Commercial
  types, applies validateOnCallSchedule for On-Call and resolveOptionalDelivery
  for non-On-Call delivery, then saves via onUpdateOrder, updateOrderInSupabase,
  and a local cache. The Delivery Address field is visually marked required, but
  the save handler currently enforces only name and 10-digit mobile.
- OrderStatusDrawer / POSModule OrderStatusSidePanel: 4-tab lifecycle drawers
  (Order Details, Activity History, Payment Info, Collection Info). Timelines are
  synthesized from stored activity_history/audit_logs/logs with fallback events.
- ThermalReceiptModal: Formats print-ready 80mm thermal receipts with store logo,
  barcode, QR code, itemized billing, and tax breakdown.

4.6 Walk-In Address & Delivery Scheduling Updates
- Create modal: Walk-In/new-customer addresses are optional and stored as NULL;
  On-Call addresses are required. Delivery date/time are optional with both-or-none
  and future-only validation.
- Inline edit, OrdersV2EditDrawer, and SideEditPanel: non-On-Call delivery uses
  resolveOptionalDelivery; On-Call uses validateOnCallSchedule in existing-order
  mode and remains legacy-tolerant for unchanged past pickups.
- POSModule full edit exception: handleSaveOrderEdit validates schedules only for
  On-Call and persists scheduled pickup/delivery only for On-Call; it does not
  add/update optional Walk-In delivery. Quick status updates do not revalidate schedules.
- OrdersV2Counter quick-intake exception: it uses On-Call-only validation and
  stores "Counter Walk-In" as an address placeholder for blank addresses.
- Display: On-Call Order Summary rows show Scheduled Pickup and Scheduled Delivery;
  all non-On-Call rows show Scheduled Delivery only. Valid delivery renders as
  "20 Nov 2026, 05:30 PM", or "Not Scheduled" when no valid value exists.


5. DATA FLOW PIPELINES
--------------------------------------------------------------------------------

5.1 Order Creation Flow:
OrdersV2CreateOrder.jsx (handleSave or direct handleCreateDirect) -> schedule
validation (validateOnCallSchedule / resolveOptionalDelivery) -> calculateOrderTotals()
-> buildCustomerData() -> createOrderWithCustomer() in customerService.js ->
cleanPayload() (empty strings to NULL) -> mobile-based customer lookup or
getNextCustomerId() -> INSERT customers for new customers (blank address to NULL)
-> getNextOrderId()/formatOrderId() -> INSERT customer_works with normalized
intake_method, work_status 'Received', scheduled_pickup_at (On-Call only),
scheduled_delivery_at (Walk-In or On-Call when supplied), and address NULL when blank
-> INSERT washdoor_orders_master -> UPSERT washdoor_factory_orders ->
saveOrderItems() + syncGarmentCardsAndInspections() -> recordAuditLogEntry() ->
recordPaymentLedger() and recordStatusHistory() when advance paid -> order note,
customer message and notification -> return {order_id, order_number, customer_id,
isNewCustomer, status:'success'} -> onOrderSuccess() -> parent onRefreshOrders().
Creation persists schedule timestamps as columns on customer_works and
washdoor_orders_master; it does not insert washdoor_pickup_delivery_schedules rows.
The Step 1 direct Create Order action uses this same pipeline with empty items and
no Step 2 review. The separate OrdersV2Counter shortcut has the exceptions noted
in section 4.6.

5.2 Order Query & Normalization Flow:
OrdersV2.jsx -> onRefreshOrders() -> getOrders() in customerService.js ->
SELECT FROM customer_works -> mapCustomerWorkRow() -> normalizeOrder() ->
restoreOrderPricing() -> normalizeOrdersV2Status() -> Multi-field filters ->
useOrdersPagination() -> Render Table & 4 KPI cards.

5.3 Order Update & Inline Edit Flow:
OrdersV2List.jsx (Inline Stepper) / OrdersV2EditDrawer.jsx / SideEditPanel.jsx ->
pre-save validation (On-Call address/schedule via validateOnCallSchedule; non-On-Call
delivery via resolveOptionalDelivery) -> updateOrderInSupabase() (alias of updateOrder)
-> customerService.js -> UPDATE customer_works with delivery_address NULL for empty
strings and scheduled_pickup_at/scheduled_delivery_at set or cleared -> merge
internal_notes, activity_history, audit_logs, payment/collection metadata ->
saveOrderItems() and syncGarmentCardsAndInspections() when item/inspection payloads
are present -> recordPickupDeliverySchedule() when schedule-slot fields are present
-> recordStatusHistory()/recordPaymentLedger()/recordAuditLogEntry() as applicable ->
onUpdateOrder() -> onRefreshOrders(). POSModule handleSaveOrderEdit and
handleQuickStatusUpdate have the On-Call/quick-update exceptions noted in section 4.6.

5.4 Dynamic Service Types Sync Flow:
ServiceTypeSelect.jsx -> "+ Add New Service Type" -> createServiceType() in
serviceTypeService.js -> Supabase: INSERT washdoor_service_types -> Dispatch DOM
CustomEvent 'washdoor_service_types_updated' -> OrdersV2.jsx listener re-fetches
service types via fetchServiceTypes() -> Real-time dropdown and badge updates.

5.5 Garment Inspection & Photos Flow:
GarmentInspectionSection.jsx -> Upload photo -> uploadGarmentPhotos() in
customerService.js -> Supabase Storage: upload to bucket 'washdoor-garment-photos' ->
Supabase DB: INSERT washdoor_garment_photos -> Updates inspection card state.

5.6 Order Deletion Flow:
OrdersV2List.jsx -> Delete icon -> Confirm dialog -> deleteOrderFromSupabase() ->
Supabase: DELETE FROM customer_works (ON DELETE CASCADE removes items, cards,
schedules, ledger) -> INSERT washdoor_audit_logs ('DELETE') -> onDeleteOrder() ->
onRefreshOrders().

5.7 Scheduled Delivery Persistence & Display Flow:
Create modal / Inline Edit / OrdersV2EditDrawer / SideEditPanel ->
validateOnCallSchedule() for On-Call or resolveOptionalDelivery() for non-On-Call ->
ISO scheduled_delivery_at -> createOrderWithCustomer() / updateOrderInSupabase() ->
Supabase mapped row -> mapCustomerWorkRow() -> resolveDisplayScheduledDelivery() ->
formatScheduledDateTime() -> Order Summary in POSModule.jsx and OrderStatusDrawer.jsx.
Fallback order: scheduled_delivery_at, scheduledDeliveryAt, then legacy paired
scheduled_delivery_date/delivery_date + scheduled_delivery_time/delivery_time.
Unparseable values are ignored; if no valid value remains, the drawers pass the
explicit "Not Scheduled" fallback. On-Call rows show pickup and delivery; other
intake types show delivery only. Pickup is never derived from delivery data.
